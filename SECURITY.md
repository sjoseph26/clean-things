# Security and disclosure

Report account-access or data-exposure findings privately to the repository owners. Include reproducible steps with fictional data. Do not put passwords, tokens, payment images or customer details in public issues.

The client contains only a public Supabase key. Authorization is enforced by PostgreSQL row-level policies and RPC ownership checks. Administrator access comes from the protected profile role, not UI flags or sign-up metadata. Payment images are private, tied to the owner's booking and accessed with short-lived signed URLs. The native WebView grants geolocation only to its bundled HTTPS origin and disables file access and mixed content.

Local demo access uses explicit customer and administrator role buttons, without passwords or a connection to a backend. Do not treat demo mode as secure multi-user storage. Connected-mode UI records are memory-only. From v0.6.3, Android session tokens persist in an AES-256-GCM file in `getNoBackupFilesDir()`, with a 256-bit Android Keystore key. The key is non-exportable; hardware backing depends on the device. Browser previews keep tokens only in JavaScript memory. Native migration erases the old localStorage token after a successful encrypted write. A failed migration leaves the existing legacy copy pending but does not use it to authenticate; a visible warning requests restart or fresh sign-in. New writes never fall back to plaintext storage.

The storage bridge exposes only read/write/clear, is enabled only for the bundled `/assets/index.html` document, and is removed during destruction. External main documents are blocked or opened in another app. CSP blocks child frames, objects and workers. `addJavascriptInterface` is not inherently origin-aware, so these document/frame restrictions are part of the security boundary and must remain in place. Arbitrary HTML, remote scripts and third-party frames must never be introduced into this WebView. Tokens necessarily exist in runtime JavaScript memory for API calls; encryption at rest does not prevent same-origin XSS, an unlocked-device attacker or a compromised OS from using an active session.

Logout clears the in-memory session, token ciphertext and token Keystore key (the optional saved login is retained until Forget saved login), and attempts server revocation even if device clearing reports a failure. Failures are visible. A copied access token can remain valid until expiry. Base encrypted storage, optional device biometrics and server-enforced administrator MFA are separate controls; see the feature sections below.

On 29 September 2026 the live token endpoint limit was reduced from 150 to 60 requests per five minutes per IP. This shared bucket covers password grants and session refreshes; it is not a five-attempt account lockout. Other endpoint limits were retained. A bounded direct-API test observed HTTP 429. Monitor shared-network users and adjust if legitimate refresh traffic is affected. Revert the token limit to 150 in Authentication > Rate Limits if this change causes operational problems.

The app honours Retry-After when supplied and uses a 60-second local backoff otherwise. Recovery resends have a separate 60-second local wait. Countdown deadlines are stored in tab session storage without account identifiers or credentials. These controls improve usability only; clearing app data does not remove Supabase's server enforcement. Password errors and recovery-success messages avoid exposing account existence; provider-internal server diagnostics are not displayed during authentication.

Custom SMTP and the recovery landing page were inspected, and one recovery-email request for the authorised owner was accepted. Inbox delivery, actual password replacement, expired/used-token rejection and subsequent sign-in still require an end-to-end test with the account owner. No password was changed during this work. See [security verification](docs/evidence/security-20260929/README.md).

The automated checks are a regression suite, not a penetration-test certification. Physical-device verification, real Storage API tests, production recovery and a live race test remain release gates. See [test scope](docs/TEST-PLAN.md).

## Staged administrator MFA (v0.6.4)

The feature branch adds mandatory TOTP verification for administrators with matching SQL enforcement. `public.is_admin()` requires an admin profile, `aal2` from `auth.jwt()`, and an existing verified TOTP factor. Customer ownership policies still allow ordinary customer actions and an admin's own-profile bootstrap. The app checks the status RPC before loading administrator records and again after verifying the code. Missing enforcement is a blocked rollout state, not a security downgrade. Provider code verification and throttling remain authoritative; the client never computes or accepts TOTP codes itself.

Setup QR SVG is rendered as an encoded image, never executable HTML. Setup secrets and input codes are not persisted. Challenge/verify requests are serialized with token renewal, bind to the current login generation, and cannot overwrite a later account or undo logout. Backup TOTP factors are supported. Removal in the app is restricted to unverified factors. Lost-factor recovery requires an identity-checked action by the project owner through privileged provider controls; there is no client-side reset bypass. See [activation and recovery instructions](docs/ADMIN-MFA-ROLLOUT.md). Live enforcement remains pending coordinated rollout and has not changed current tester access.

## Optional saved-login biometric sign-in (v0.6.8)

This replaces the v0.6.5–v0.6.7 app-lock feature. There is no lock screen, manual lock or background timer. Session tokens use ordinary encrypted storage independently from an optional saved email/password. Password login must succeed first, and the user must explicitly tick Save login before the native save prompt opens. Cancelled saving leaves password login successful and preserves any previous saved login.

`SavedLoginVault` keeps the email, password and verified user ID in a separate AES-256-GCM envelope in `getNoBackupFilesDir()`. A random data key is wrapped by an Android Keystore key requiring `BIOMETRIC_STRONG` for each operation. Android 11+ is required. Each replacement creates a new wrapping-key alias, commits atomically, then deletes the previous alias. Cancelled replacement deletes only the pending key. Biometric enrolment changes invalidate the key. Any qualifying biometric enrolled on the device can authorize use of its saved login; consent text states this. Fingerprint/face templates never enter the app.

The trusted-document login bridge exposes status/save/use/cancel/forget/take, separately from session read/write/clear. Callbacks carry only request IDs and outcomes. Credentials can be taken once after native authenticated decryption; forged success events cannot produce them. Decrypted credentials exist briefly in runtime memory for the server password grant and are not put in events, logs, browser storage or application state. Java/JavaScript strings and provider copies cannot be guaranteed physically erased; mutable byte buffers are wiped on completion/cancellation. Same-origin XSS, root and OS compromise remain outside the encryption boundary.

Every biometric sign-in makes a fresh Supabase password grant and binds the response to the saved user ID before storing tokens. Network access and a still-valid password/account are required. Login rate limits, profile/role checks and administrator MFA remain in force. Biometrics do not elevate tokens to AAL2 and are not passkeys. Logout cancels pending operations, clears active tokens and attempts local-session revocation, while deliberately retaining the encrypted saved login. Forget saved login deletes only the credential record and its keys; it does not end an active session. Generation checks reject late sign-in responses after logout or forgetting.

An upgrade from the old biometric session lock requires one password sign-in; legacy locked session ciphertext is never used as saved credentials. The user can then tick Save login. Physical Android Keystore/sensor acceptance remains required. The separate staged administrator MFA rollout has not been activated.
